## 摘要
随着端侧LLM智能体演变为个人智能副驾，移动操作系统已成为这一范式的关键试验场，因此严格的能力评估不可或缺。然而，现有基准可分为两类，且各自存在关键盲点：以GUI为中心的基准测试考察表层的屏幕操作，却忽视了后台工具使用与长时程规划；而静态函数调用基准则依赖离线API匹配，与真实运行时约束脱节。为弥补这一空白，我们提出MobilePA-Bench，一个交互式、有状态且以工具为中心的基准，用于评估移动规划智能体的工具调用与规划能力。MobilePA-Bench运行在可执行沙箱中，该沙箱维护实时应用数据库并返回结构化反馈，涵盖13个功能领域和212个真实移动工具。除基本工具使用外，它还从三个高级维度评估中心规划智能体：(1) 子智能体协作——将复杂任务分解，并把专门工作委派给有能力的子智能体；(2) 记忆使用——回忆存储的记忆、用户画像和过往偏好，以解决隐式请求；(3) 技能使用——调用预打包的复合技能，而非从零开始规划每一步。大量实验表明，当前前沿LLM在移动场景中仍不可靠：在严格的工具调用顺序、权限限制和意外运行时错误下，性能急剧下降。通过将交互式函数调用沙箱与基于证据的验证相结合，MobilePA-Bench既可作为实用的诊断基准，也可作为智能体强化学习的交互式基础，从而加速可靠移动智能体的开发。

## Abstract
As on-device LLM agents evolve into personal copilots, the mobile operating system has become a key testbed for this paradigm, making rigorous capability evaluation essential. Yet existing benchmarks fall into two camps, each with a critical blind spot: GUI-centric benchmarks test surface-level screen manipulation while overlooking background tool use and long-horizon planning, whereas static function-calling benchmarks rely on offline API matching that is detached from real runtime constraints. To close this gap, we present \textbf{MobilePA-Bench}, an interactive, stateful, and tool-centric benchmark for evaluating the tool-calling and planning abilities of mobile planning agents. MobilePA-Bench runs on an executable sandbox that maintains live application databases and returns structured feedback, spanning $13$ functional domains and $212$ realistic mobile tools. Beyond basic tool use, it evaluates a central planning agent along three advanced dimensions: \emph{(1)~Sub-agent Collaboration}---decomposing a complex task and delegating specialized work to capable sub-agents; \emph{(2)~Memory Usage}---recalling stored memories, user profiles, and past preferences to resolve implicit requests; and \emph{(3)~Skill Usage}---invoking pre-packaged composite skills instead of planning every step from scratch. Extensive experiments show that current frontier LLMs remain unreliable in mobile settings: performance drops sharply under strict tool ordering, permission limits, and unexpected runtime errors. By pairing an interactive function-calling sandbox with evidence-based verification, MobilePA-Bench serves as both a practical diagnostic benchmark and an interactive foundation for agentic reinforcement learning---accelerating the development of dependable mobile agents.

## 1. 核心问题与研究动机

- **背景**：随着端侧 LLM 智能体从被动对话走向"个人智能副驾"，移动操作系统成为关键试验场。真实用户意图（如"规划下周三去上海的三日游"）无法靠单纯 API 调用或 GUI 自动化完成，而需要**记忆检索 + 结构化 API 批处理 + 多模态输入处理 + API 不可用时回退到视觉 UI 交互**的混合编排。
- **现有基准的两类盲区**：
  - **GUI 中心基准**（AndroidWorld、OSWorld、WindowsAgentArena、MobiBench、MobiFlow）：只测像素级屏幕操作与布局感知，忽视后台工具调用与长时程规划，且渲染/VNC 开销大、吞吐低。
  - **静态函数调用基准**（BFCL v1–v4、ToolBench、DroidCall、AppBench、TAU-Bench）：依赖离线字符串/JSON 匹配，缺乏有状态运行环境，无法测试动态 OS 反馈、权限边界与运行时异常恢复。
  - 高级能力基准（MemGPT、VOYAGER、SkillBench、OpenCLAW）则各自孤立评估记忆/技能/子智能体，缺乏真实移动工作流整合。
- **整体含义**：论文主张"原始屏幕点击只占移动智能的一小部分"，应将**中心规划与低层视觉解析解耦**，用一个交互式、有状态、以工具为中心的沙箱，统一诊断移动规划智能体的四维能力。

## 2. 方法论

### 2.1 核心思想
- 将移动智能形式化为**工具中心的编排闭环**：中心规划智能体做高层推理，直接调用结构化业务 API，检索记忆、加载复合技能、并在必要时把专门工作委派给子智能体（其中 GUI 子智能体负责视觉落地与界面操作）。

### 2.2 形式化流程
- 任务定义为四元组：用户意图 *q*、初始状态 S₀、可选对话历史 H₀、活跃候选动作集 A₀。
- 每步规划：**aₜ = π(q, Hₜ, Aₜ)**；沙箱执行：**(Sₜ₊₁, fₜ) = Exec(Sₜ, aₜ)**；历史累积：**Hₜ₊₁ = Hₜ ⊕ (aₜ, fₜ)**。
- 循环直至发出 `Finish` 或达到最大步数 **T_max = 15**；成功与否由轨迹 H_T 与终态 S_T 事后验证。

### 2.3 统一动作空间（四类接口）
- **Direct Mobile Tools**（Basic Tool Use）：直接查询/变更模拟系统状态的 API。
- **Sub-agent Entry Tools**（Sub-agent Collaboration）：路由到专门子智能体的入口，参数含目标路由与任务指令，返回执行状态与反馈。
- **Memory Tools**（Memory Usage）：如 `search_user_memory`，返回排序后的记忆记录，需规划器显式查询并融入后续规划。
- **Skill Loading Tools**（Skill Usage）：元接口，触发动作空间动态扩展；加载技能后 **Aₜ₊₁ = Aₜ ∪ G(s)**，否则 Aₜ₊₁ = Aₜ。
- 初始动作空间：**A₀ = R_N(q, H₀; G) ∪ L_q**，其中 R_N 为 top-N 召回工具模式，实验中 **N = 15**。

### 2.4 有状态仿真沙箱
- 环境状态：**Sₜ = ⟨Dₜ, Oₜ⟩**（Dₜ 为实时应用数据库，Oₜ 为操作日志）。
- 反馈格式：**fₜ = ⟨Status, ErrorType, Payload⟩**。
- 三层结构：**Tool Schema**（函数签名/参数/领域标签）→ **Tool Code**（参数校验、实体重复检查、ID 生成等执行逻辑）→ **Shared Stateful Database**（状态变更 + 审计日志）。
- 在初始状态 S₀ 中**注入受控环境摩擦**：缺参、权限阻断、实体歧义等，迫使规划器读取反馈并实时修复计划。
- 因不涉及重渲染，支持**高吞吐、确定性执行与轨迹回放**，适合强化学习 rollout。

### 2.5 基于证据的对齐验证（三个 Query Bucket）
- **Bucket 1: Tool Call**：要求工具名、调用顺序、参数字段与归一化取值严格匹配，且不得有多余副作用调用。
- **Bucket 2: State Change**：允许多条有效路径，验证终态数据库增量 **D_T − D₀** 与标注目标增量一致，并拒绝破坏性或无关写操作。
- **Bucket 3: Agent Behavior**：针对开放式/交互式任务，用任务专属 rubric 评估两项指标——**(i) 是否调用合适子智能体（Call Sub-agent）**；**(ii) 后续行为是否合理（澄清提问、呈现选项等）**。
- **能力门控**：
  - 记忆门控 **g_mem(q) = 1 ⟺ M*_q ⊆ M̂_T**（检索到的记忆 ID 集合包含全部金标记忆）。
  - 技能门控 **g_skill(q) = 1 ⟺ s*_q ∈ K̂_T**（轨迹中加载了金标技能）。
  - 联合成功 **Succ(q) = g(q) ∧ C_b(q)(H_T, S_T)**，即门控与主检查器同时通过。

### 2.6 评分聚合
- **Score_overall = 0.50×Basic + 0.10×SubAgent + 0.20×Memory + 0.20×Skill**，采用**全分母、不可变**评分（缺失或非法预测记为失败）。
- 权重设计体现"有状态工具执行是基础（50%）"，同时给复杂推理、个性化与多智能体协调以显著权重。

### 2.7 任务构建维度
- **Basic Tool Use** 五类行为：工具与参数接地、条件与依赖规划、指代与状态追踪、意图修改与任务管理、边界检测与错误恢复。
- **Sub-agent Collaboration**：记录有效下游路由与交接所需的上下文载荷。
- **Memory Usage**：基于连贯用户画像世界合成，请求故意省略显式偏好，需先查记忆再规划，记录金标记忆 ID。
- **Skill Usage**：把多步复合例程封装为可复用技能包，标注金标技能 ID 与执行目标，分别在 **SOR（纯技能路由）** 与 **MTSR（工具-技能混合路由）** 下评估。

## 6. 主要结论与发现

- **整体上限偏低**：最强模型 Claude-Opus-5 总体加权分仅 **75.52%**，13 个模型中有 **7 个低于 70%**，即使最强规划器失败率仍 ≥ 24.48%。
- **维度间落差巨大**：Basic Tool Use 最高 **83.85%**（均值 76.58%），而 Sub-agent Collaboration 区间 **43.82%–77.53%**、Memory Usage 区间 **33.78%–64.63%**（均值仅 50.98%），个性化记忆是最薄弱环节。
- **不存在全面占优的规划器**：Claude-Opus-5 领先 Basic（83.85%）与 Skill（78.00%），Gemini-3.1-Pro 领先 Sub-agent（77.53%，但 Memory 仅 48.67%），Qwen-3.8-Max 领先 Memory（64.63%）——能力呈碎片化分布。
- **复合技能复用可缓解长时程误差累积**：Skill Usage 达 78.00%，且对多数模型高于 Memory，说明预打包多步流程比从原子工具逐步规划更稳

健；MTSR（工具-技能混合路由）相对纯原子工具规划也表现更优，提示"技能封装"是压缩长时程规划搜索空间的有效手段。
- **错误会跨能力级联**：案例剖析显示，一次失败的记忆检索往往导致后续工具参数接地错误，进而触发无效状态写入——低层工具调用的错误会向上污染高层编排，说明四个能力维度并非彼此独立，而是存在**上游决定下游**的依赖链。
- **编排意图与端到端执行脱节**：多个模型能正确"说出"该调用哪个子智能体、该加载哪个技能（Bucket 3 的 Call Sub-agent 判定较高），但后续实际状态变更或参数填充失败，暴露出**"规划正确 ≠ 执行落地"**的落差。
- **缺乏校准的克制与自适应恢复**：模型普遍在权限被阻断、实体歧义或参数缺失时，倾向继续盲目重试或直接放弃，而非读取 `ErrorType` 后主动澄清、切换路径或降级到子智能体；这类"恢复行为"的缺失是总体分数被拉低的重要来源。
- **稳定性结论**：Qwen3.6-27B 三次完整重跑均值波动极小，说明沙箱执行的**确定性**设计有效（同轨迹可复现），但 Sub-agent 子集因样本量小仍存在题目级别的翻转风险。

## 7. 局限性

- **算力信息完全缺失**：既无评测硬件描述，也无总推理成本、token 消耗或时间开销，复现者难以预估评测门槛。
- **基准自身设计未做消融**：受控摩擦的注入类型与强度、四项能力权重（0.50/0.10/0.20/0.20）、N=15 候选召回、T_max=15 步预算、Query Bucket 划分方式均为主观设定，缺少敏感性分析与理论依据。
- **子集样本不平衡**：Sub-agent Collaboration 仅 89 题，却占 10% 权重，单题影响约 1.12 分；记忆维度 376 题中多轮与单轮、DB-primary 与 API-primary 各半，但未报告跨子类的分层结果。
- **验证主观性风险**：Bucket 3 依赖任务专属 rubric 与子智能体路由标注，论文未报告标注者间一致性（IAA）或人工复核比例，开放式任务的评分可复现性存疑。
- **缺少人类基线与跨基准对照**：无法判断 75.52% 相对人类水平的位置，也未与 AndroidWorld、BFCL、DroidCall 等在同一批模型上做横向对照，因此"现有基准有盲区"这一核心论断缺乏直接的量化证据。
- **仿真而非真机**：沙箱虽保证确定性与高吞吐，但真实移动 OS 的权限弹窗、网络抖动、传感器噪声、应用版本差异等未被建模，向真机迁移的外部效度有待验证。
- **仅评推理不评训练**：论文定位为诊断性评测，未展示该沙箱用于强化学习 rollout 或微调的实际增益，对"能否提升智能体能力"缺少闭环证据。

## 8. 启示与展望

- **方法论价值**：MobilePA-Bench 提出了一种"**中心规划与视觉落地解耦**"的评测范式——把 GUI 操作降级为子智能体的一种委派目标，而把结构化 API、记忆、技能、子智能体协作提升为一等公民，这为移动智能体评测提供了新的组织原则。
- **能力碎片化提示研究方向**：没有任何模型在四维上全面领先，说明当前规划器在"通用编排"与"个性化记忆"之间存在权衡；未来的训练目标或架构设计需显式处理这种多目标张力。
- **错误恢复是下一个瓶颈**：既然基础工具调用已达 76.58% 均值、技能复用达 66.77%，进一步提分的边际收益可能更多来自**运行时异常感知与自适应重规划**，而非再增加工具覆盖。
- **基础设施开源的意义**：全量开源沙箱、工具 schema、状态数据库与验证器，使研究者能在同一确定性环境下对比提示工程、记忆架构、多智能体路由策略，降低该方向的可复现门槛。
- **可扩展方向**：引入人机对照、跨基准交叉评测、摩擦强度消融、真实设备回放，以及把该沙箱接入 RL 训练回路，均是后续工作的自然延伸。

## 9. 一句话总评

MobilePA-Bench 用一个**有状态、以工具为中心、支持记忆与技能动态扩展的移动沙箱**，把"移动智能体能力"拆解为四维可诊断指标，并以 1,705 个真实任务、13 个前沿模型的实证，揭示了当前最强规划器总体上限仅 75.52%、个性化记忆与子智能体协作显著拖后腿、且错误会跨能力级联的核心结论；其最大贡献在于**评测范式的转向与全量开源**，最大短板在于**自身设计缺少消融、算力信息缺失、验证主观性未校验**。
