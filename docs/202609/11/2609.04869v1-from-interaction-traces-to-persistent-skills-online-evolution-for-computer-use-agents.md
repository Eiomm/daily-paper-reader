## 摘要
计算机使用智能体能够在图形界面中执行日益复杂的任务，但其交互经验通常是短暂的：从一次 rollout 中获得的过程性知识不会被系统地保留、精炼并在后续任务中复用。现有技能库提供了外部程序性知识，但相对于同一智能体在不使用技能时的运行，其增量价值，以及重复交互下的纵向动态，仍未得到充分刻画。我们提出一个在线技能演化框架，将交互轨迹和评估器反馈转化为持久化、带版本的可复用过程库。每一轮迭代都基于冻结的技能库快照执行，而由证据引导的技能更新会在后续迭代中可用，且不改变模型参数。我们在四个 OSWorld 应用领域上，比较完整的演化技能库系统与配置匹配的空技能库对照组，二者使用相同的固定动作生成与 GUI 定位技术栈、任务集和迭代轮数。在五轮空技能库预热之后，Full 在所有四个观测到的领域运行中，预热后的平均评估器得分都更高，平均差异范围为 5.7 至 18.6 个百分点，且时间稳定性因领域而异。在 GIMP 中，溯源感知分析揭示了跨原始任务边界的检索和修订反复变动，其中反复被接受的编辑未能恢复原始任务。这些发现将演化技能库刻画为可审计的共享程序性记忆，能够改进固定的计算机使用技术栈，同时表明其收益是有条件的，且重复修订并不保证恢复。代码已在 https://github.com/LongtaoHu/Skill-Evo4GUI 发布。

## Abstract
Computer-use agents can execute increasingly complex tasks in graphical interfaces, but their interaction experience is typically transient: procedural knowledge acquired from one rollout is not systematically retained, refined, and reused in later tasks. Existing skill libraries provide external procedural knowledge, yet their incremental value over the same agent operating without skills, as well as their longitudinal dynamics under repeated interaction, remain insufficiently characterized. We present an online skill-evolution framework that converts interaction trajectories and evaluator feedback into a persistent, versioned library of reusable procedures. Each iteration executes against a frozen library snapshot, and evidence-guided skill updates become available in subsequent iterations without changing model parameters. We compare the full evolving-library system with a configuration-matched empty-library control across four OSWorld application domains under the same fixed action-generation and GUI-grounding stack, task sets, and iteration horizons. Following a five-iteration empty-library warm-up, Full attains a higher post-warm-up mean evaluator score in all four observed domain runs, with mean differences ranging from 5.7 to 18.6 percentage points and domain-dependent temporal stability. In GIMP, provenance-aware analysis reveals retrieval across task-of-origin boundaries and revision churn, where repeated accepted edits fail to recover the originating task. These findings characterize evolving skill libraries as auditable, shared procedural memory that can improve a fixed computer-use stack, while showing that their benefits are conditional and repeated revision does not guarantee recovery. Code is released at https://github.com/LongtaoHu/Skill-Evo4GUI.

## 1. 核心问题与整体含义

- **背景**：计算机使用智能体（Computer-Use Agents）已能在图形界面中执行复杂长程任务（如 WebArena、OSWorld 所评测的场景），但交互经验通常是**短暂**的——一次 rollout 中获得的过程性知识、失败证据、应用专属操作经验不会被系统性保留、精炼和复用，导致智能体反复"重新发现"同一流程或重复同一失败。
- **已有工作的缺口**：现有技能库（Reflexion、ExpeL、Voyager、Agent Workflow Memory、CUA-Skill、MMSkills 等）提供了外部程序性知识，但两个问题刻画不足：
  1. **增量价值不明**：演化技能库相对于同一智能体在**无技能**条件下重复交互，究竟带来多少增益？
  2. **纵向动态不明**：技能库在重复成功/失败下如何演化？是否支持超出技能来源任务的复用？
- **整体含义**：论文主张把演化技能库视为**可审计的、共享的程序性记忆（procedural memory）**，它能在**不改变模型参数**的前提下为固定的计算机使用栈带来可测的改进；但这种收益是**有条件的、依领域而异的**，反复修订并不保证任务恢复。

## 2. 方法论

- **核心思想**：把执行（read-only）与演化（write-enabled）**严格分离**。每轮迭代在**冻结的技能库快照**下执行固定任务集，执行结束后再由轨迹证据引导技能库变更，变更仅在下一次快照中可见，从而避免"边执行边改库"的混淆。
- **四阶段流水线（Figure 1）**：
  1. **运行时执行**：固定 Executor（EvoCUA-32B）根据任务指令与截图选择工具调用；坐标相关动作由固定 Grounding 模型（MVP）映射为绝对像素坐标，经 pyautogui 执行。技能**不直接执行 GUI 动作**，仍须经过同一 Executor 工具接口与 Grounding。
  2. **轨迹抽象**：Extractor 将轨迹 τ 与辅助证据 E 转为结构化事实 F，包含任务摘要、结果、逐步 state–action–effect 记录、聚合模式、能力限制、技能调用观察。**评估器分数覆盖模型自述**；telemetry 中缺失的技能调用被删除，telemetry 有而 Extractor 遗漏的调用被恢复为"结果不确定"。
  3. **在线技能演化**：Proposer 诊断最多 5 轮历史事实与当前库元数据，输出 `create_new / edit_existing / delete_existing / no_op / unresolved` 提案（含目标与理由，只给高层意图）；Coordinator 校验（决策 schema、领域技能名前缀、创建需 5 次观察、重名/超尺寸门控降级为 no_op、unresolved 需窗口内至少 2 次失败）；Skill Builder 生成**完整技能文档**（编辑为整体替换而非文本补丁），删除则不调用 Builder。
  4. **持久技能库**：每次成功变更作为独立 **Git commit** 写入，保留修订历史与贡献任务。下一轮导出快照 S_{t+1} 供执行。
- **公式化表述**：
  - 轨迹生成：τ^c_{t,i} = Execute(q_i; S^c_t)，即同一轮内所有任务共享同一冻结快照。
  - 库状态：Full 在 t=0…4 为空（预热），Empty 全程为空；Full 的首个非空执行快照出现在 t=5。
  - 域级得分：Score^c_{d,t} = 100 × (1/N_d) Σ_i s^c_{d,t,i}，s∈[0,1]，可含部分分。
- **渐进式检索**：每轮开始时仅解析 SKILL.md 的 name/description 渲染为 Markdown 目录放入 Executor 提示；Executor 判断相关时调用 `get_skill(name, reasoning)` 取回完整技能正文。目录与 get_skill 均为只读，无法看到当轮提交的修订。
- **溯源机制**：技能创建时固定其**来源任务**；每次接受编辑记录贡献任务与结果修订；每次检索记录消费任务、迭代轮次、交付修订及与下游结果（成功/持续失败/部分进展/不确定）的**观察性关联**。消费者任务≠来源任务即为**跨来源检索**。telemetry 只证明"检索了什么"，不构成因果归因。
- **演化执行细节**：采用**串行决策模式**，按任务 ID 固定顺序处理，后一个提案可看到同一轮更早的 commit，因此**顺序依赖**；无自动整合或回滚。

  - GIMP：26 任务 / 35 轮（OSWorld 参考 76%）
  - VLC：17 任务 / 20 轮（参考 49%）
  - LibreOffice Writer：23 任务 / 20 轮（参考 69%）

## 5. 实验数量与充分性

- **实验规模**：4 个应用域 × 2 个条件（Full/Empty）= **8 条独立纵向运行**；每个条件–域对**仅运行一次**。GIMP 上额外进行技能级溯源分析（最终库 27 个技能）。**没有消融实验**（如单独去掉 Proposer、去掉跨来源检索、不同检索策略等），也**没有在未见任务上的迁移测试**。
- **充分性不足**：
  - 单次运行导致随机波动无法估计，**无显著性检验**，结果只是"描述性比较"而非因果估计。
  - **预热不平衡是混杂因素**：Full 与 Empty 独立执行，预热期（t=0–4）轨迹并不重合。GIMP（−4.0pp）与 Thunderbird（−6.7pp）预热期为负，之后反转；VLC 从 +4.7 扩大到 +18.6；**Writer 在空库预热期已相差 +9.1pp**，其 +11.8pp 的预热后差异大部分无法唯一归因于技能可用性。
  - 固定任务集反复执行测的是**集内适应**，而非对未见任务的泛化。
  - 溯源分析只覆盖 GIMP 一个域。
- **公平性方面**：配置匹配（同栈、同任务、同轮数、同接口）是设计上的优点；但上述预热不平衡与单次运行削弱了因果解释力。总体而言，实验**方向性可信但统计效力与覆盖度不足**。

## 6. 主要结论与发现

- **性能**：预热后（t≥5）Full 在**全部四个域**的平均评估器得分均高于 Empty 对照，差值 **5.7–18.6 个百分点**（GIMP +5.7、VLC +18.6、Writer +11.8、Thunderbird +12.4）；差异幅度与时间稳定性**依域而异**，且**非均匀、非单调**（GIMP 有多次交叉）。
- **共享记忆的证据**：GIMP 最终库含 27 个技能，**82.4% 的有效 rollout 至少调用一次 get_skill**；记录的技能调用中 **56.7% 检索本任务来源的技能，43.3% 为跨来源检索**——说明技能库被当作跨任务共享的程序性记忆使用，而非仅任务专属存储。
- **修订churn**：背景透明化任务派生出三个相关技能（gimp-select-uniform-background、gimp-remove-uniform-background、gimp-add-alpha-channel），其中 gimp-add-alpha-channel 反复被接受编辑，但**35 轮中仅成功 2 次（5.7%）**——失败证据持续诱发库变更却无对应改善，构成"修订churn"，与固定 Executor–Grounding 栈存在瓶颈一致（但该案例本身无法定位瓶颈在技能选择、动作生成还是定位）。
- **总体定位**：演化技能库可改善固定计算机使用栈，但收益有条件、不保证；检索本身不等于遵循或受益。

## 7. 优点

- **问题切分清晰**：把"参数内学习"与"外部程序性记忆"解耦，在 Executor/Grounding 完全固定下考察技能库的净增量，研究问题正交且有价值。
- **执行与演化分离的机制设计**：迭代冻结快照避免了执行期看到未验证修订，使适应过程**可观测、可复现、可归因**，且不引入模型微调或 rollout 内适应。
- **配置匹配的纵向对照**：Full 与 Empty 使用相同栈、任务集、顺序、轮数与接口，最大程度控制变量。
- **溯源与版本化**：Git commit 级版本化 + 来源任务/编辑历史/检索消费任务/下游结果关联，使技能生命周期**可审计**；跨来源检索比例提供了共享记忆的直接（观察性）证据。
- **数据可靠性处理细致**：评估器分数覆盖模型自述、telemetry 与 Extractor 记录双向校正、Coordinator 的创建/编辑门控（5 次观察、尺寸门控、unresolved 需 2 次失败），降低噪声与幻觉写入。
- **渐进式检索**：目录只暴露元数据、正文按需拉取，节省上下文并保留显式检索理由。
- **学术诚实**：明确承认单次运行、预热混杂、非因果、churn 现象，并给出可执行的后续方向；代码开源。

## 8. 不足与局限

- **统计效力弱**：每个条件–域对仅一次独立运行，无重复、无方差估计、无显著性检验；结论为描述性比较。
- **因果归因受限**：预热期两条件已分离（尤其 Writer +9.1pp），使预热后差异不能唯一归因于技能可用性；跨来源检索与下游结果仅为观察性关联，单次 rollout 可能检索多个技能，结果还受模型行为与环境状态影响。
- **任务设置限制**：重复固定任务集测的是集内适应，**无法回答未见任务迁移**；OSWorld 外部参考分不是匹配基线，仅作区间标定。
- **覆盖不全**：详细溯源只在 GIMP 上进行，其他三域缺乏技能级分析；无消融实验，无法分解框架各组件（Proposer、Coordinator、渐进式检索、版本化）的贡献。
- **机制限制**：技能只是**文本程序性指导**，GUI 动作仍须经固定 Executor–Grounding 执行，因此**无法修复底层的动作生成或坐标定位失败**（churn 案例即为此类瓶颈的体现）；串行演化**顺序依赖**，且**缺少自动整合与回滚**机制。
- **应用与风险**：收益依领域而异、非单调，意味着部署时需按域评估；反复无效修订可能浪费演化预算甚至污染库；技能库长期膨胀可能带来检索干扰（论文未量化）。
- **资源报告缺失**：未提供任何算力/成本信息，影响可复现性与规模评估。
- **未来方向**：多次重复运行、留出任务、组件消融、直接测量技能遵循度；在无额外 Grounding 模块的原生动作生成智能体上验证；用强化学习优化 Proposer 的演化策略，以奖励下游改进、惩罚无效修订。
