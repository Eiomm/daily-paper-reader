## 摘要
持久记忆正在进入面向生产的智能体平台，以帮助长时程智能体跨会话积累经验。然而，仅限于已完成轨迹的任务后整理智能体可能会保留错误、过度泛化部分证据或保留过时知识。我们提出环境探查式整理，这是一种与部署兼容的扩展，赋予现有异步整理智能体最小权限的只读世界工具，以核查、限定范围并刷新候选记忆。它无需重新训练模型，且不改变任务智能体、检索器、记忆表示和生产写入权限。在基于其 SDK 构建的类生产 GitHub Copilot (GHCP) 测试框架中，我们在 CLBench 数据库探索和 90 个改编的 APEX 管理咨询任务上比较了无状态执行、完整上下文学习、GHCP + Mem 以及 GHCP + Mem（带环境探查）。在 CLBench 上，环境探查将通过率从 39% 提升至 73%，将按通过率折算的奖励从 8.60 提升至 22.60，同时将每个问题的查询次数从 8.8 降至 4.7，并将任务智能体成本从 $3.38 降至 $1.68。在六个 APEX 世界中，全部 18 项记忆与基线的平均奖励比较均为正向，任务智能体的工具调用次数下降 16%–75%；在五个世界中，环境探查带来每美元最高的任务智能体奖励增益。在 Sonnet 4.6 和 Opus 4.7 上，环境探查均比 GHCP + Mem 获得更高的平均奖励，且未出现 schema 漂移。因此，环境探查将现有的智能体记忆整理转变为一种基于环境信息、可审计的过程，同时保留紧凑的任务时接口。

## Abstract
Persistent memory is entering production-oriented agent platforms to help long-horizon agents accumulate experience across sessions. Yet a post-task curator agent restricted to completed trajectories can preserve errors, overgeneralize partial evidence, or retain stale knowledge. We introduce environment-probing curation, a deployment-compatible extension that gives an existing asynchronous curator agent least-privilege, read-only world tools to check, scope, and refresh candidate memories. It requires no model retraining and leaves the task agent, retriever, memory representation, and production write authority unchanged. In a production-like GitHub Copilot (GHCP) harness built on its SDK, we compare stateless execution, full in-context learning, GHCP + Mem, and GHCP + Mem (w/ Env Probing) on CLBench database exploration and 90 adapted APEX management-consulting tasks. On CLBench, probing raises pass rate from 39% to 73% and pass-discounted reward from 8.60 to 22.60 while reducing queries from 8.8 to 4.7 per question and task-agent cost from \$3.38 to \$1.68. Across six APEX worlds, all 18 memory-versus-baseline mean reward comparisons are positive and task-agent tool calls fall by 16--75%; probing gives the best task-agent reward gain per dollar in five worlds. Probing also attains higher mean reward than GHCP + Mem on both Sonnet 4.6 and Opus 4.7 without schema drift. Environment probing therefore turns existing agent-memory curation into an environment-informed, auditable process while preserving a compact task-time interface.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体正从"单次任务执行"走向"跨会话持续工作"（如代码库演进中的功能开发、企业数据分析、客户支持）。成功依赖于积累反馈，尤其是对**跨任务共享的潜在环境结构**的认知。
- **现状缺陷**：无状态执行在会话边界丢弃轨迹、观测与错误；而引入外部持久记忆后，**仅依赖"已完成轨迹"进行任务后整理（post-task curation）的 curator 智能体存在根本性的证据边界不完备问题**。
- **具体失效模式**（论文归纳为 5 类）：
  - 记住某个实例答案而非其可复用流程；
  - 继承低效的探索路径；
  - 断言无法验证的适用范围；
  - 在未访问区域留下盲区；
  - 随环境漂移（drift）而变得过时。
- **后果**：把验证推迟到任务时，会迫使响应智能体花稀缺的工具调用去复核不确定的记忆，而非直接解题。
- **核心命题**：轨迹只是对环境的**单次、局部、常含错误的观测**；更强的反思（reflection）也无法恢复任务策略从未观测到的状态，或判断规则在环境漂移后是否仍成立。

## 2. 方法论

### 2.1 核心思想
**环境探查式整理（Environment-Probing Curation）**：在不重训模型、不改动任务智能体 / 检索器 / 记忆表示 / 生产写入权限的前提下，仅给**异步 curator 智能体**授予**最小权限、只读**的世界工具，使其在写入记忆前主动核查、限定范围、刷新候选记忆。

### 2.2 系统角色与工具边界（Figure 1）
- **任务智能体 Aθ**：每个任务开启全新会话，持有环境工具 T_Ei 与**只读** `memory_read`，无记忆写权限；产出原始轨迹 τᵢ。
- **蒸馏器 Dψ**（非写入预处理）：把 τᵢ 转成紧凑的蒸馏轨迹 dᵢ = Dψ(τᵢ)，**不接收终端反馈**、无记忆/环境工具，只保留任务、检索到的记忆、关键观测、流程、未决假设与答案。
- **Curator 智能体 Cφ**：任务结束后独立实例化，接收 dᵢ、终端反馈 gᵢ 与相关既有记录，独享四个记忆工具：`memory_read / create / update / delete`；整理在 Sᵢ₊₁ 揭示前完成，杜绝未来任务泄漏与部分写入进入任务执行。

### 2.3 记忆记录契约
每条记录包含：`category`（pattern | rule | trap | schema | policy | interaction）、`confidence`、`applies_to`（检索范围）、`lemma`（简明可执行主张）、provenance、utility 与使用元数据。

### 2.4 环境探查机制（Propose–Probe–Commit）
在原始 curator prompt 上**仅插入两段**（P_probe = P_curator + A_access + A_verify）：
1. **只读工具访问声明**（插入 Available Tools 下）；
2. **验证提示**（插入 Check 与 Reconcile 之间）：当正确性、范围、时效性或可操作性不确定时，使用只读环境工具验证候选与既有记忆。

可执行的探查动作：
- 区分偶然答案与可复用关系；
- 比较已观测流程与更短路径；
- 在另一数据切片上测试所声称的关系；
- 检查流程所需前置条件；
- 检查轨迹遗漏的相关状态；
- 怀疑漂移时重新查询当前环境。

**约束**：探查只能评估候选记忆，不得解题、不得改变环境、不计入任务智能体预算、不暴露未来任务或标签；若不存在安全的只读界面，则回退到纯轨迹整理。

### 2.5 奖励公式
任务 i 的按通过率折算奖励：**rᵢ = pᵢ · (1 − qᵢ / B)**
- pᵢ ∈ {0,1}：严格通过（多评分标准时需全部通过）；
- qᵢ：基准计数的任务智能体工具调用数（排除记忆管理与框架内部调用）；
- B：CLBench 为 15 次 SQL 查询，APEX 为 100 次 Archipelago 工具调用。

## 6. 主要结论与发现

1. **记忆本身即有效**：所有记忆配置在 CLBench 上同时提升正确率与折扣奖励（通过率 39% → 61–73%，奖励 8.60 → 20.00–22.60，约 2.3–2.6 倍），并把查询从 8.8 降至 3.0–5.6，成本从 $3.38 降至 $1.68–$2.01——说明记忆让智能体更可能通过且更少重复发现 schema/编码/工具约定。
2. **索引式记忆优于全上下文**：Full ICL 查询最少但消耗 5.42M 输入 token；索引记忆 2.13M；探查记忆仅 1.69M 且通过率与奖励最高。记忆避免了任务时上下文随部署年龄线性增长。
3. **探查在漂移边界即已领先**：迁移点处累计奖励 0.541 vs 0.486，终点 0.565 vs 0.500（无记忆 0.215）——与"curator 侧探查在后继任务检索前刷新 schema lemma"一致，而非让每个任务智能体独立检测漂移。
4. **跨模型泛化**：无漂移下，Sonnet 4.6 提升 +0.351（Mem）/+0.421（Probe），Opus 4.7 为 +0.252/+0.263；探查在两模型上平均奖励最高（0.748 与 0.721）。
5. **APEX 上效率与正确性双赢**：18/18 奖励增益为正；工具调用从基线均值 30.0–71.6 降至 13.9–28.4（降 16–75%）；探查在 6 个世界中的 5 个取得每美元最高奖励增益。工具削减本身可**促成正确性**（为最终计算留出预算），而非仅降低延迟。
6. **探查效果取决于"剩余证据缺口"**：在轨迹已支持可执行记录时增益有限（941eba66 为 −0.04）；在 join、工作簿位置或流程未解决时增益最大（2a87e5cb +1.77、2f84c98b +1.09）；Sonnet 增益（+0.075）大于 Opus（+0.025）。
7. **定性证据**：纯轨迹整理易产出"答案锚定的警告""缺少关系的宽泛映射""漂移后失效的表名"；探查整理产出**可执行流程**（明确的源表、join 键、过滤条件、聚合粒度、当前 schema）。匹配案例中查询数从 7/9/8 降至 1/2/1（CLBench），APEX 中从 96 次调用失败降至 11 次（Mem）与 6 次（Probe）。

## 7. 优点

- **方法极简且部署兼容**：不改模型、任务智能体、检索器、记录 schema 与异步 CRUD 生命周期；只需给 curator 已注册连接器/MCP 工具的**只读子集**，沿用平台认证、授权与审计边界，无需第二条集成路径。
- **权限设计克制**：探查无写权限、不改变环境、不进入任务轨迹、不消耗任务预算、不暴露未来任务与标签；无安全只读界面时优雅降级为纯轨迹整理。
- **因果归因干净**：通过固定任务时接口与 CRUD 生命周期，把增益严格隔离到"写入期证据质量"。
- **成本感知的评测**：引入按通过率折算的奖励 rᵢ = pᵢ(1 − qᵢ/B)，同时报告通过率、工具调用、token 与美元成本，并把记忆管理与整理阶段单独记账，避免用隐藏开销美化结果。
- **多模型、多基准、配对随机化**：3 个模型家族、2 类企业任务、配对基线与置信区间，结论稳健性较好。
- **定性 + 定量互补**：不仅给数字，还用并排记录与匹配轨迹说明"为何有效"，把机制落到可执行的具体差异上。
- **认知科学呼应**：与情景记忆的"重构性"（Bartlett；Schacter 等）和交互式学习（Sukhbaatar 等）的理论联系，为设计提供额外合理性论据。

## 8. 不足与局限

- **算力信息缺失**：未报告任何 GPU 型号/数量/时长；虽然方法无需训练，但**探查阶段的端到端成本与延迟未完整披露**，难以评估总拥有成本。
- **探查机制缺少消融**：未系统分离"只读工具本身""验证提示""探查预算/次数"各自的贡献；也未测试探查过度（over-probing）或探查引入

错误/污染的风险。
- **记忆质量的长程衰减未评估**：实验只覆盖 40 题（CLBench）与 90 题（APEX），未验证在数百至上千次会话、多次连续漂移下，curator 的探查是否能持续抑制记忆陈旧化，也未测量记忆库规模增长对检索精度与探查成本的影响。
- **探查的收益边界未被刻画为可预测信号**：论文观察到"剩余证据缺口"决定增益大小（941eba66 上甚至为 −0.04），但未给出一个**事前可计算的判据**（例如轨迹中未决假设数、schema 引用覆盖率）来预测何时值得探查，实践中仍需试错。
- **环境假设较强**：方法要求存在**安全、只读、低成本**的环境接口；对于副作用不可逆、查询昂贵或权限边界模糊的系统（如生产数据库直连、真实客户系统），探查可能不可行或代价过高，论文未讨论这类受限场景的替代方案。
- **蒸馏器 Dψ 未被消融**：蒸馏轨迹 dᵢ 是 curator 的唯一输入，其压缩率、保留哪些观测（是否保留未决假设、错误、工具调用序列）会显著影响探查起点，但论文固定了蒸馏器，未考察其与探查的交互。
- **成本核算不完整**：如第 4 节所述，蒸馏与 curator 阶段（含探查工具调用）的成本/延迟仅被"单独跟踪"却未在正文完整披露，导致"探查更省"的结论只覆盖任务智能体响应阶段，**端到端总拥有成本仍是开放问题**。
- **评测环境为自建 harness**：GHCP 测试框架基于 SDK 自建，虽贴近生产但非公开标准；APEX 子集经筛选（480 → 90 题、按世界分组），存在选择偏差风险，跨厂商 harness 的独立复现缺失。
- **缺少人工评估**：记忆记录的可读性、可维护性、是否便于人类审核与纠错未做评估，而这在企业落地中往往是关键约束。
- **统计稳健性有限**：APEX 部分子组置信区间重叠，作者自述只能作"机制解释"；CLBench 主实验 5 次运行，对高方差任务的效应估计仍偏弱。

## 9. 可复现性与实践启示

- **可复现性**：方法层面完全基于 prompt 与工具接口，理论上易于复现；但论文未提供代码、prompt 全文、记忆记录样本或数据划分细节（仅给出实验协议），加之使用自建 GHCP harness 与专有模型（GPT-5.4/Sonnet 4.6/Opus 4.7），**独立复现门槛较高**。
- **对工程实践的启示**：
  - 若已有异步 curator 与记忆 CRUD 流水线，**只需追加只读工具暴露 + 一段验证指令**即可尝试，改造成本极低；
  - 优先把探查用在"关系型/流程型"候选记忆（join、前置条件、工作簿定位）上，对已验证的稳定事实不必探查；
  - 应把探查工具调用与任务预算严格隔离，并复用平台的认证/审计边界，避免引入第二条权限路径；
  - 对无安全只读接口的环境，应显式降级为纯轨迹整理，而非冒险探查。

## 10. 总体评价

- **贡献定位**：论文的核心洞见——**轨迹只是环境的单次局部观测，仅靠事后反思无法补全证据缺口，必须允许 curator 在写入前以只读方式主动核查环境**——是清晰且可证伪的。它把"记忆质量"问题从"如何更好地总结轨迹"重构为"如何在写入期获取充分证据"，视角有价值。
- **方法优点**：极简、低侵入、权限克制、因果归因干净，并配有成本感知的奖励指标；在企业智能体的既有架构上具备较高可落地性。
- **证据强度**：跨 3 个模型、2 类企业任务、配对随机化与置信区间的组合，使"探查整理优于纯轨迹整理"这一主结论具有中等偏强的支持；定性案例进一步增强了机制可信度。
- **主要短板**：探查机制的消融、端到端成本核算、长程记忆衰减、探查收益的事前预测、以及受限环境下的适用性均未充分展开，限制了结论从"有效"走向"可预测、可运维"。
- **一句话结论**：这是一篇**方法简洁、动机扎实、工程友好**的工作，它论证了"给 curator 一双只读的眼睛"能实质提升企业智能体记忆的可执行性与时效性；但其收益的边界条件、总成本与长期鲁棒性仍待后续研究补齐。
